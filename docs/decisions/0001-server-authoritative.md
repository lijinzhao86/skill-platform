# ADR 0001 · 服务端权威，本地不落 skill 副本

- **状态**：已采纳
- **日期**：2026-09-26
- **取代**：无

## 背景

让 agent 用上 skill，有两条根本不同的路：

- **(a) 下发到客户端磁盘**，靠客户端原生的分层加载（`~/.agents/skills/` 一类落点）。现成的生态（Vercel 的 `skills` CLI、80 个 agent）就是这么工作的。
- **(b) 内容只留在服务端**，客户端通过远程地址按需读取。

同时产品定位是"**托管服务**"——用户把 skill 托管在远程，通过远程服务访问。

## 决定

采用 **(b)**。**服务端是 skill 的唯一真相，本地不落任何 skill 副本。**

客户端侧只装两样东西：一个网关 skill 与一个 CLI（见 [ADR 0002](0002-gateway-skill-and-cli.md)）。

## 理由

- **与定位一致。** "远程托管"的意义就是内容在服务端；把内容下载到本地再靠客户端加载，等于把托管退化成"分发压缩包"。
- **渐进加载变成接口层的强制，而不是模型的自觉。** 搜索接口只返回 L1、正文接口只返回 L2、文件接口只返回 L3——服务端**在物理上**不给多余的层。若内容已经下发，分层与门控就只能靠客户端配合。
- **任何后续商业化形态都成立。** "未授权内容不下发"在这个模型下是天然属性，不需要另建机制；而在下发模型里，内容一旦落盘就收不回（撤销、封禁、更新都无法即时生效）。
- 免除了"内容落盘后无法撤回"这一整类问题。

## 后果

- **本地唯一常驻的是网关 skill，L1 的上下文成本从 O(N) 降到 O(1)。** 本机 30 个真实 SKILL.md 实测：每个 skill 的 L1 平均 318 字符、其中约 33% 是 CJK 字符，折算**约 160 tokens**；500 个全量安装约 **8 万 tokens** 常驻（口径见[技术设计 §1.6](../versions/v1-hosting/technical-design.md)）。网关模型下只有 1 个。
- 客户端必须有可用的 HTTP 能力（我们的 CLI，或裸 `curl`）。
- **离线不可用**——这是选择服务端权威的固有代价，不试图绕过。
- `skill_platform/materializer.py`（把目录渲染到本地）**基本作废**，仅保留归档/导出的可能性。
- agent 为完成任务而产生的中间产物（如 `curl -o` 下来的文件）落到本地是允许的——那与"安装一份 skill 副本"是两回事。
