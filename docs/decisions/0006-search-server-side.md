# ADR 0006 · 检索在服务端，且只索引 L1

- **状态**：已采纳
- **日期**：2026-09-26
- **依赖**：[ADR 0001](0001-server-authoritative.md)、[ADR 0002](0002-gateway-skill-and-cli.md)
- **后续**：「后果」里那条中文分词选型（SQLite FTS5 + `trigram`）已由 [ADR 0010](0010-storage-in-postgres.md) 取代（实测不可行）。**正文四段保持原样**——改写它就丢掉了「当时是这么想的」，这是 ADR 不可变的代价。

## 背景

服务端权威（[0001](0001-server-authoritative.md)）之后，客户端不常驻目录。于是"有哪些 skill 可用"只能问服务端。

同时，Agent Skills 的三层里只有 L1（frontmatter 的 `name` + `description`）是公开可索引的：L2 是正文、L3 是文件，都是"按需才取"的内容。

## 决定

- **搜索、排序、查找全部在服务端实现。** 客户端不做任何本地索引。
- **只索引 L1**（标准的 `name` + `description`，**外加平台自己的 `title` 元数据字段**），**绝不索引正文或文件内容**。
- **P0 的排序公式必须可解释**：`w1 × 文本相关性 + w2 × 新鲜度 + w3 × 人工权重`。

## 理由

- **这不是可选的实现细节，是架构的必然。** 目录不常驻，服务端就是索引本身。
- **只索引 L1 是安全约束，不是性能考虑。** 正文一旦进全文索引，就可能通过片段检索被反推出来——即使当前不做收费，这条也应该守住，因为它决定了内容的暴露面。
- **排序质量在这个模型下就是产品的核心。** 网关的 `description` 决定"该不该去查库"，而排序决定"查到的是不是对的"。两者一起构成全部的发现体验。因此排序必须**可解释、可调、可回归测试**——不能是一个说不清为什么的黑盒。

## 后果

- 检索从"附属功能"变成最需要投入的部分。需要建立**回归任务集**：给 N 个真实任务，检查"该不该查库"与"查到的是否正确"。
- **中文分词需要选型**：计划 SQLite FTS5 + `trigram` tokenizer（对中文子串匹配可用），**需实测目标构建是否带该 tokenizer**；不带则退回 `LIKE` 或引入外部索引。
- **使用信号要落表**（曝光 / 详情 / 正文读取 / 文件读取），供 P1 用真实信号改进排序。P0 没有这些数据，只能用启发式。
- 服务端在接口层强制分层：搜索接口物理上拿不到正文——这也是渐进加载的实现方式。
