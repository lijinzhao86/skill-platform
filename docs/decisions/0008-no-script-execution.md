# ADR 0008 · P0 不做脚本执行

- **状态**：已采纳
- **日期**：2026-09-26
- **依赖**：[ADR 0001](0001-server-authoritative.md)

## 背景

skill 目录里的 `scripts/` 需要被执行才能真正发挥价值。在服务端权威模型下，脚本也在服务器上，于是"谁来执行"成为一个必须选择的岔路：

- **服务端沙箱执行**——真正什么都不落客户端磁盘，但要建隔离、资源限制、密钥不泄露这一整块工程。
- **返回给客户端本地执行**——实现简单，但脚本就落到了客户端磁盘上，与 [ADR 0001](0001-server-authoritative.md) 的前提矛盾。

## 决定

P0 **不提供脚本执行能力**，只做"读取与使用"（正文与文件都能读到，怎么处理由调用方决定）。

## 理由

- 服务端沙箱是独立的硬工程，原产品文档本就把它排在最后阶段。
- 两条执行路径各自与既有前提冲突：沙箱太重，客户端执行破坏"不落盘"。
- 先把最核心的那条链路验证通——**托管 → 远程检索 → 按需读取 → 使用**——再决定执行形态。执行形态依赖真实使用场景，现在定等于猜。
- 覆盖面损失可以接受：本机实测 30 个真实 skill 中有 9 个**没有任何 L3 文件**，其中 5 个有实质正文（工作流型，如会议纪要、周报、API 探索）。这类 skill 在 P0 完全可用。

## 后果

- P0 覆盖**纯正文 + 参考文档型** skill；需要脚本的 skill 只能读到脚本内容。
- **脚本执行形态是一个未决的架构岔路**，需要时可新增 ADR 决定。它也影响上传校验策略（要不要扫脚本、要不要限制脚本类型）。
- 若要往回走补执行能力，两份前置工作需要先做：上传时的脚本扫描策略，以及沙箱方案（若选服务端执行）。
