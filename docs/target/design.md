## 第 0 章 · 机制与设计原则

### 核心机制：渐进加载 = 渐进付费

Claude Code 式 skill 的加载天然是分层的：frontmatter 常驻上下文，正文被触发时才读，引用的资源文件与脚本在真正需要时才打开。skill-platform 把这三层直接当作**计费节点**。

一次上传会自动派生出四类节点：

| 节点 | 来源 | 默认定价 | 角色 |
|---|---|---|---|
| `l1` | SKILL.md frontmatter（name + description） | 免费 | 发现层：搜索、卡片流、榜单都只基于它 |
| `l2` | SKILL.md 正文中首个细切标记**之前**的部分 | 免费 | 试用层：让用户判断"这东西对我有用吗" |
| `l2#n` | 正文中每个细切标记切出的一段 | 免费（作者可改） | 细分层：做成"前几节免费、后面付费" |
| `l3:<relpath>` | skill 目录里的每个文件 | 付费（默认建议价） | 交付层：脚本、配置、数据集 |

> **为什么选渐进付费、为什么不按次也不按整包**，完整论证见蓝图第 6 章。本文只从「这样切分之后，系统要怎么做」出发。

### 三条产品原则

1. **发现层永远免费。** L1 收费等于自我灭绝——没有 L1 就没有搜索与推荐，也就没有流量入口。这条原则在模块 6（发现与浏览）里落成"只索引 L1"的实现约束。
2. **价值必须下沉到可执行层。** 默认把 L2 免费，是在逼作者把真正的价值做成脚本与资源，而不是写成一段散文。这条原则在模块 3 里落成上传时的分级引导。
3. **撞墙必须优雅降级。** Agent 拿不到付费节点时不能崩，要拿到 teaser 并继续把不需要该节点的部分做完。用户感受到的应该是"有个可选升级"，不是"失败了"。这条原则在模块 5 里落成运行时协议。

### 设计边界

蓝图第 9 章已界定产品不做什么。其中三条会直接约束模块划分：

- **不是 npm。** npm 一次发布全网可装；skill-platform 是按主体分层授权，同一份 skill 对不同人呈现不同深度——这决定了「分发」必须带权限计算，不能是简单复制。
- **不是 GPT Store。** 那里卖封装好的黑箱 agent；skill-platform 卖可被 agent 自己拆开、按需加载的中间层——这决定了节点必须与官方加载层严格对应，不能自定义切分。
- **不是文档库。** skill-platform 内容里的一等公民是可执行的脚本与资源——这决定了 L3 的落盘与门控是核心路径，不是附属功能。

三个必须在**设计层**正面承接的风险（论证见蓝图 Q1 / Q8 / Q6）：

| 风险 | 设计上的承接 |
|---|---|
| 防不住复制 | 解锁记录保留内容哈希与主体，支持事后追溯与指认 |
| L3 作为默认付费点反向约束作者 | 上传时做分级诊断；保留 `l2#n` 细切作为正文型 skill 的退路 |
| 买断 + 自动更新是代码注入通道 | 需要行级版本状态、changelog 与买家可选的版本锁定 |

## 第 1 章 · 角色与权限模型

### 人类角色

| 角色 | 范围 | 能做什么 |
|---|---|---|
| 平台管理员 | 平台级 | 管理组织、发放钱包额度、审核、封禁、处理争议 |
| 组织管理员 | 组织内 | 管理成员、组织预算、组织级授权 |
| 作者 | 自己上传的 skill | 上传、定价、看数据、下架 |
| 消费者 | 自己 | 浏览、解锁、使用、充值 |

一个用户可以同时是多个 skill 的作者，也是别的 skill 的消费者。这四个角色不是互斥的身份层级，而是**在同一用户身上的能力集合**。

### 非人类主体（必须单列）

它们不是"用户"，但是真实的行为主体，模型里必须有一等公民的地位。

**Agent 运行时。** 它是唯一真正触发付费墙的主体。它代消费者持有两样委托：

- **预算**：本次会话或本周期最多能花多少。
- **策略**：撞墙时怎么办（见模块 5 的三策略）。

它的行为必须是可预测、可审计的，且**不能自主扩权**——agent 不能自己提高预算上限，不能自己改变策略。预算与策略只能由人类在会话开始前设定，或在撞墙时由人类当场授予。

**组织。** 可以有钱包、有权益、有成员。组织权益是其成员权益的**并集来源**：成员个人没买，但组织买了，成员就可用。

### 三层权限关系

从外到内，逐层收窄：

```
① 可见性 visibility     能否发现这个 skill
     public      所有人可搜到
     org         仅组织成员可搜到
     private     仅作者与显式被授权者
     unlisted    不可搜到，但拿到链接可访问

② 节点权益 entitlement   能看到哪一层
     free        免费节点
     purchased   买断获得
     granted     被显式授权（管理员/作者发放）
     subscription 订阅获得（M3）

③ 否决 denial            最高优先级，覆盖以上一切
```

**可见性与付费是正交的两个维度。** `public` 只代表"能被搜到"，不代表内容免费——一个 public skill 完全可以 L1 免费、L3 收费。这正是"免费发现层 + 付费内容"的落点。这个正交性必须在界面上说清，否则用户会误以为"公开 = 免费"，作者也会误以为"设为 public 就没法收钱了"。

### 权益解析顺序

```
作者本人 → 否决 → 仅作者可见 → 公开 → 个人权益 → 组织权益 → 私有 → 全局默认
```

两个不可动摇的次序约束：

- **否决必须在个人与组织权益之前。** 否则封禁对一个买了内容的组织成员无效——而封禁恰恰最常用于这种人。
- **组织权益是补充而非覆盖。** 个人买过而组织没买，个人仍然可用；反之亦然。两层是并集，但否决高于并集。

## 第 2 章 · 模块划分

八个模块。每个模块统一说明：**职责 / 边界（明确不做什么）/ 关键对象 / 依赖 / 阶段**。

---

### 2.1 身份与组织

**职责**
平台自有账号体系；注册、登录、会话；第三方身份绑定（飞书**仅作 SSO 跳转鉴权**，不作为主键）；组织创建与成员管理；角色分配。

**边界（不做）**
- 不存储第三方密码，不代管组织外的身份。
- 不做通讯录双向同步——飞书是登录入口，不是成员数据源。
- M1 不做注册登录界面（内部场景由管理员建号），界面在 M2。

**关键对象**：`User`、`Identity(provider, external_id)`、`Org`、`Membership(role)`

**依赖**：无（最底层）

**阶段**：M1 建表与基础方法 / M2 注册登录与 SSO 跳转 / M3 实名（公开市场的前置）

**为什么必须解耦飞书**：如果把 `open_id` 当用户主键，将来接 GitHub、微信、邮箱登录都要改主键，等于每一条外键都得迁移。把"身份提供方"降级成 `Identity` 里的一行，未来接新 provider 只是加一行数据。

---

### 2.2 Skill 托管与版本

**职责**
上传与导入（目录树或压缩包）；SKILL.md 解析（frontmatter + 正文）；文件清单与二进制存储；可见性设置；审核状态；版本序列。

**边界（不做）**
- M1–M2 不做在线 SKILL.md 编辑器。
- 不自动生成 skill 内容，不替作者写作。
- 不做跨 skill 的内容去重（M3 若需要再议）。

**关键对象**：`Skill`、`SkillFile`、`Version`、`Visibility`、`ReviewStatus`

**依赖**：身份与组织（owner）

**阶段**：M1 导入 + 可见性 + 版本快照 / M2 上传界面 + 在线元数据编辑 / M3 审核队列

**版本策略（已锁定）**：买断即获得后续更新。这意味着用户买的不是"某个版本"，而是"这个节点"。因此：

- **版本号不参与定价**，只用于审计与注入防护。
- 用户没有"我买的是 v1 还是 v2"的概念，界面上不应暴露版本选择（锁定版本是安全功能，不是购买选项）。

---

### 2.3 节点、定价与权益（核心模块）

**职责**
从上传内容自动派生节点；解析细切标记；维护价格表；给出默认价建议；节点级权益解析。

**边界（不做）**
- 不根据内容自动定价——只给建议，最终定价权在作者。
- M3 前不允许作者对同一节点按用户差别定价（避免"杀熟"质疑与实现复杂度）。
- 不做跨 skill 的捆绑定价。

**关键对象**：`Node(kind, node_id, relpath, title, teaser, price)`、`Price(source, override, effective)`、`Entitlement(subject, node, source)`

**依赖**：Skill 托管

**阶段**：M1 全部核心 / M2 可视化定价表 / M3 促销与动态定价

#### 设计点一：teaser 比价格重要

付费前展示的那句话决定转化率。用户撞墙时看到的不是"¥5"，而是"这一段会用脚本一次处理 100 条，省掉你 20 分钟手工"——价格只是决策的最后一个变量。

因此：**付费节点的 teaser 是必填项，为空不允许发布。** 这是产品规则，不是可选的元数据。

#### 设计点二：源价与覆盖价分离

作者群体有两类，必须同时服务：

| 作者类型 | 定价入口 | 价格来源 |
|---|---|---|
| 技术型 | SKILL.md 里的声明 | 跟随 git，PR 可评审、可回滚 |
| 产品型 | 平台 console 的定价表 | 即时生效，无需改代码 |

规则：**有效价 = 覆盖价 ?? 源价**。console 改价写入覆盖价并置为粘性；作者想回到源码价就清除覆盖价。这样两条路都不丢，也不会出现"谁覆盖谁"的歧义。

#### 设计点三：节点派生与价格保留

每次导入都要重新派生节点集合（标记与文件会变），但**价格必须存活**——否则作者改一句文案就把定价全冲掉。

规则：

- 节点已存在 → **不动其价格**（沿用现有代码里 `access` 字段的同一套惯用法）。
- 节点消失（作者删了标记或文件）→ 节点删除，但**其上的权益保留为孤儿**。用户付过钱，节点以后回来了他仍然拥有。这也意味着权益记录不能对节点做强外键约束。

### 2.4 交易、钱包与结算

**职责**
钱包（个人 / 组织）；充值；订单与幂等；解锁事务；组织预算与审批；退款；平台抽成与作者结算。

**边界（不做）**
- M1 不接真实支付通道，由管理员记账充值。
- 不做信贷、后付费、分期。

**关键对象**：`Wallet`、`WalletEntry`（流水账）、`Order(idempotency_key)`、`Split`

**依赖**：节点权益、身份与组织

**阶段**：M1 钱包 + 充值记账 + 解锁 + 订单 / M2 组织预算与审批流 / M3 支付通道 + 抽成结算 + 退款争议

#### 解锁必须是一个原子事务

```
校验未拥有 → 校验余额充足 → 扣款 → 写订单 → 写权益
```

这五步之间不能有窗口。否则并发下会重复扣款，或余额被扣成负数。工程上必须写成**单个事务**，且不能复用各自的公开方法（它们各自的连接不构成同一事务）。这条是硬约束，实现时不可"看起来差不多"地拆开。

幂等键的意义：agent 重试、网络抖动、用户连点，都必须只扣一次。幂等键应包含主体、节点与会话标识。

#### 钱包与流水

钱包记**当前余额**（快路径，解锁时的条件扣款依赖它），同时记**流水账**（审计与对账）。两者在同一事务内写入，不允许出现余额与流水对不上的状态。

### 2.5 分发与运行时门控（核心模块）

**职责**
把授权结果渲染成运行时能加载的目录树；未解锁节点不下发；定义运行时付费墙协议；离线降级；解锁事件上报。

**边界（不做）**
- M3 前不代理执行 skill 的脚本（不沙箱、不托管运行时）。
- 不修改模型对内容的呈现方式。
- 不做端侧加密（若未来需要，属于本模块的独立子课题）。

**关键对象**：`MaterializePlan`、`LockedManifest`、`GateDecision`、`PaywallPolicy`

**依赖**：节点权益、Skill 托管

**阶段**：M1 全部核心（用本地缓存实现 Gate）/ M2 远程 Gate + 离线策略 / M3 服务端按节点下发

#### 现有实现的结构性冲突（必须改）

现有 materializer 把 skill 的所有内容**一次性全部落盘**。只要落盘，付费墙就是装饰。新行为分三部分：

1. **SKILL.md 由已解锁的段落重新拼装**：frontmatter + 已解锁的 L2 段落；未解锁的段落替换为**占位块**，内含 teaser 与价格。这样 agent 看得见"这里有更深的内容"，而不是看到一个被截断的残文件。
2. **L3 文件只落已解锁的**。未解锁的文件在磁盘上不存在。
3. **在 skill 目录写一份机器可读的 locked manifest**，列出被锁的节点、价格与 teaser。运行时据此准确报告"还差什么"，而不是靠猜。

#### 运行时付费墙协议

```
agent 需要 l3:scripts/run.py
        ↓
EntitlementGate.check(subject, skill, node)
        ↓ 命中 → 返回内容，继续执行
        ↓ 未命中 → 返回 GateDecision(paywall, price, teaser)
        ↓
按 PaywallPolicy 三选一执行：
```

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `ask` | 暂停 agent，向人类出示解锁卡，等待决定 | 交互式会话，**默认** |
| `auto_under(N)` | 价格 ≤ N 则自动扣款并继续 | 自动化 / 无人值守 agent |
| `deny` | 跳过该节点，继续完成其余部分 | 防止 agent 在循环里反复撞墙 |

`deny` 不是"失败模式"，它是有意义的产品行为：一个 agent 在批处理循环里每轮都撞同一堵墙，如果默认 `ask`，用户会被问 200 次。`deny` 让 agent 走降级路径。

#### 优雅降级的具体形态

撞墙时 agent 应该：**拿到 teaser → 告知用户"这里有个更省事的做法，需要 X 元解锁" → 用不需要该节点的路径把任务做完。**

对比两种体验：

- 差的：`Error: skill l3 node locked`，任务中断。
- 好的：`已用基础流程完成报表（12 步）。另有一个脚本节点可把这一步降到 1 步，需 ¥5 解锁。`

后者把一个失败变成了一个可选升级。

### 2.6 发现与浏览

**职责**
搜索；分类与标签；L1 卡片流；榜单；作者主页。

**边界（不做）**
- M3 前不做个性化推荐算法，用简单排序（解锁量、更新时间）。
- **不索引付费内容**（见下）。

**关键对象**：`SkillCard`（即 L1）、`SearchIndex`（仅 L1）、`Tag`、`Ranking`

**依赖**：Skill 托管

**阶段**：M1 CLI 列出 / M2 console 浏览与搜索 / M3 推荐与榜单

**只索引 L1。** 这不是性能考量，是安全约束：L2/L3 是付费内容，一旦进入全文索引，就可能通过片段检索被反推出内容。索引范围必须硬性限制在 L1（name + description）。

---

### 2.7 数据洞察

**职责**
作者看板——每个节点的曝光、解锁、跳过；转化漏斗；平台看板。

**边界（不做）**
- M1–M2 不向作者暴露消费者身份，只给聚合数据。
- 不做竞品定价分析。

**关键对象**：`NodeEvent(曝光, 撞墙, 解锁, 跳过)`、`Funnel`、`AuthorDashboard`

**依赖**：节点权益、交易

**阶段**：M1 记录事件 / M2 作者看板 / M3 平台看板与漏斗优化建议

#### 本产品给作者的独特价值

**最有价值的单个指标是「撞墙率 vs 解锁率」**——传统市场只能告诉你"卖出多少"，skill-platform 能告诉你"卡在哪一层"：

| 现象 | 诊断 | 建议动作 |
|---|---|---|
| 撞 1000 次，解锁 10 次 | teaser 没写好，或价格过高 | 先改 teaser，再考虑降价 |
| 撞 100 次，解锁 90 次 | 定价偏低 | 提价，或把该节点再细切 |
| 撞 100 次，跳过 95 次 | 节点位置不对，用户不需要 | 检查是否放错了层 |

这是 skill-platform 作为"渐进付费平台"相对传统市场的核心差异化能力，值得在作者侧做成首屏。

### 2.8 信任、安全与治理

**职责**
脚本扫描与静态检查；沙箱执行；举报下架；实名；注入防护；封禁。

**边界（不做）**
- **M1 不做任何安全能力**（内部信任场景，成员之间本就不设防）。
- 不承诺 100% 拦截恶意代码——这是能力边界，必须在公开市场阶段对用户明示。

**关键对象**：`ScanResult`、`Report`、`Sanction(封禁/下架)`、`ContentHash`

**依赖**：Skill 托管、节点权益、交易（赔付与扣回）

**阶段**：M1 无 / M2 扫描 + 举报下架 / M3 沙箱 + 实名 + 官方审核队列

#### 必须正面处理的结构性风险

**买断 + 自动更新 = 免审的代码注入通道。** 这不是"实现不完善"，而是产品模型自带的通道：

> 用户 A 在 3 月解锁了 `l3:scripts/run.py`。作者在 5 月把该文件替换为窃密脚本。因为"买断即获得后续更新"，A 无感知地自动执行了它。

三层防护（对应第 0 章问题三）：

1. **更新重审**：脚本类节点的内容变更需重新过审；至少要让买家看到 diff 与显著提示，而不是静默更新。
2. **买家可控**：可见 changelog，**可选择锁定版本**——用放弃自动更新换取确定性。这是"买断即自动更新"的必要出口。
3. **可追溯**：解锁记录保留内容哈希，事后能精确定位到作者与具体版本。

#### 其他安全面

- **付费脚本是恶意代码分发面。** 公开市场允许付费脚本，就必然有人上传挖矿或窃密脚本。M3 需要沙箱执行 + 实名 + 举报通道三者齐备，缺一不可。
- **封禁需要能穿透组织权益。** 见第 1 章的次序约束。

## 第 3 章 · 核心场景

统一模板：**触发者 / 前置条件 / 主流程 / 异常分支 / 涉及模块 / 阶段**。

### S1 · 作者上传并发布含定价的 skill

**触发者**：作者
**前置**：已登录；对目标 skill 有作者权限
**主流程**
1. 作者提供源（目录树 / 压缩包 / git 源）。
2. 系统解析 SKILL.md，派生节点集合，给出默认价建议（L1/L2 免费、L3 取建议价）。
3. 作者看到定价表：每个节点的 title、teaser、价格。**付费节点的 teaser 为空时不允许发布。**
4. 作者确认可见性（public / org / private / unlisted）。
5. 发布，skill 进入已发布状态；L1 进入索引。

**异常分支**
- SKILL.md 无 frontmatter 或无 name → 拒绝导入并明确报错（不能静默生成一个无名 skill）。
- 节点派生后作者改价，随后又改 SKILL.md 重传 → 覆盖价仍在，作者的定价不会被冲掉（模块 2.3 设计点三）。
- 正文 token 占比过高 → 提示"可考虑把可执行部分下沉到 L3"，但**不阻断发布**。

**涉及模块**：2.2 托管、2.3 定价、2.6 发现、2.8 治理（M2 起）
**阶段**：M1（不含审核）/ M2 加上传界面 / M3 加审核队列

---

### S2 · 消费者发现并全程使用免费层

**触发者**：消费者
**前置**：skill 可见性允许其访问
**主流程**
1. 通过搜索或链接进入 skill 详情页，看到 L1 卡片。
2. 浏览节点树：哪些免费、哪些付费、各自 teaser。
3. 决定试用，运行时加载 L1 + L2。
4. 全程不撞墙，任务完成，零付费。

**异常分支**
- 用户在节点树里看到付费节点的 teaser，可能试图从 teaser 反推内容 → teaser 应描述**收益**而非**方法**，这是作者教育问题（写入写作指引）。
- L2 本身就足以完成任务 → 作者收不到钱。这是作者的内容分层问题，平台通过 S8 的数据反馈让作者看见。

**涉及模块**：2.6 发现、2.3 定价、2.5 分发
**阶段**：M1

### S3 · 消费者首次撞到付费墙并解锁单个节点（核心场景）

**触发者**：消费者（经由 agent）
**前置**：已读到 L2；目标 L3 节点未解锁
**主流程**
1. Agent 需要 `l3:scripts/run.py`，向 Gate 请求。
2. Gate 返回 `GateDecision(paywall, price=500, teaser="...")`。
3. 策略为 `ask` → 暂停，向用户出示解锁卡：teaser + 价格 + 节点树上下文（这个节点在整条路径的哪个位置）。
4. 用户确认 → 校验余额 → 原子解锁（扣款 + 订单 + 权益）。
5. 返回节点内容，agent 继续，任务完成。

**异常分支**
- **余额不足** → 引导充值，**不中断 agent 的其余部分**（先降级继续，充值后回来补上）。
- **重复点击 / agent 重试** → 幂等键保证只扣一次。
- **用户拒绝** → 走 `deny` 降级路径，agent 用免费路径完成其余部分。
- **该节点同时被组织权益覆盖** → 不应弹付费卡（解析顺序里组织权益先命中）。

**涉及模块**：2.3 权益、2.4 交易、2.5 门控
**阶段**：M1

---

### S4 · Agent 自动运行中撞墙（核心场景）

**触发者**：无人值守的 agent 任务
**前置**：会话开始前已设定预算与策略
**主流程**：与 S3 相同，区别在于**没有人在场**，一切由预设策略决定。

**三种策略的行为对比**

| 策略 | 撞墙时的行为 | 风险 |
|---|---|---|
| `ask` | 挂起等人类响应 | 无人值守时会一直挂着，或超时失败 |
| `auto_under(N)` | 价格 ≤ N 自动付款继续 | 预算可能被一次循环耗尽 |
| `deny` | 跳过，走降级路径 | 任务可能以低质量方式完成 |

**异常分支**
- **循环内反复撞墙** → 必须有"同一节点在同一会话内不重复询问/扣款"的去重，否则 `auto_under` 会烧光预算。
- **预算耗尽** → 后续所有付费节点自动降级为 `deny`，并在任务结束时报告"因预算用尽跳过了 N 个节点"。
- **agent 试图提高预算上限** → 必须被拒绝。预算只能由人类在会话开始前设定或当场授予。

**涉及模块**：2.5 门控、2.4 交易
**阶段**：M1（三策略 + 会话内去重）/ M2 预算耗尽报告

---

### S5 · 组织买断一个节点给全员

**触发者**：组织管理员
**前置**：组织有钱包余额；管理员有授权权限
**主流程**
1. 管理员在后台看到"本组织成员本月撞墙最多的节点"排行（来自模块 2.7 的聚合数据）。
2. 选择买断某个节点 → 从组织钱包扣款 → 写入组织权益。
3. 组织内所有成员的解析结果中，该节点由 `paywall` 变为命中组织权益，**不再弹付费卡**。

**异常分支**
- **组织已买断，但某成员被单独 `deny`** → 否决优先，该成员仍不可用（封禁必须穿透组织权益）。
- **成员在组织买断前已自费买过** → 不自动退款（M1 政策），但应在成员侧展示"你已自费解锁，组织也已覆盖"以免困惑。
- **组织余额不足** → 走审批流（M2），M1 由管理员直接充值。

**涉及模块**：2.1 身份组织、2.4 交易、2.3 权益
**阶段**：M1 买断与权益生效 / M2 审批流与数据驱动推荐 / M3 组织自助管理

---

### S6 · 作者更新内容后老买家自动获得

**触发者**：作者
**前置**：该节点已有买家
**主流程**
1. 作者上传新版本。
2. 系统按"买断即获得更新"更新所有相关买家的可用内容。
3. 买家侧看到 changelog。

**异常分支（本场景的重点）**
- **恶意更新**：作者替换脚本为恶意代码，老买家自动执行。防护见模块 2.8 三层方案——重审 / 可锁定版本 / 内容哈希追溯。
- **节点被删除**：权益保留为孤儿；节点恢复后买家仍然拥有（模块 2.3 设计点三）。
- **作者改价**：新买家按新价；老买家不受影响，也不退款。
- **更新后节点被锁得更深**（原本免费的 L2 段落变成付费）→ **不允许对已有买家的节点做此变更**，否则等于收回已售出的权益。

**涉及模块**：2.2 托管、2.3 定价、2.8 治理
**阶段**：M1 自动更新 / M2 changelog 与锁定版本 / M3 重审流程

---

### S7 · 管理员充值、查看流水、封禁

**触发者**：平台管理员
**前置**：已以管理员身份登录；目标主体（用户或组织）已存在
**主流程**
1. 给某个人或组织充值 → 写入余额与流水。
2. 查看流水：谁在什么时候为什么扣了多少。
3. 封禁某人对某 skill（或某 skill 族）的访问 → 写入否决。

**异常分支**
- **充值后用户投诉未到账** → 流水是唯一事实来源，必须能按主体与时间检索。
- **封禁一个已付费用户** → 不自动退款（M1 政策，见第 6 章待决问题）。
- **误封** → 撤销否决即恢复；其原有权益不能因封禁而丢失。

**涉及模块**：2.4 交易、2.3 权益、2.8 治理
**阶段**：M1

---

### S8 · 作者查看解锁数据并调价

**触发者**：作者
**前置**：作者拥有该 skill；已有一定量的解锁事件（否则样本不足，看板不给出调价建议）
**主流程**
1. 作者打开看板，看到每个节点的曝光 / 撞墙 / 解锁 / 跳过。
2. 按模块 2.7 的诊断表判断问题所在。
3. 改 teaser（最常见）或改价。
4. 改价即时生效于新买家，老买家不受影响。

**异常分支**
- **样本量太小** → 看板必须显示"数据不足，暂不建议调价"，避免作者被噪声误导。
- **作者大幅降价** → 提示可能引发"老买家要求补差"的预期，但不阻断。
- **作者把价格设为 0** → 该节点变为免费，已有买家权益保留（无损害）。

**涉及模块**：2.7 洞察、2.3 定价
**阶段**：M1 记录事件 / M2 看板

---

### S9 · 退款与争议处理

**触发者**：消费者 / 平台管理员
**前置**：存在一笔已完成的解锁订单；内容哈希与当时下发的 teaser 均可回溯
**主流程**
1. 用户申诉（如"解锁后发现内容无用"）。
2. 管理员查看解锁记录与内容哈希，判断是否属于"内容与 teaser 严重不符"。
3. 若成立：退还钱包余额、撤销权益、记录作者侧的质量标记。

**异常分支**
- **内容已被用户读取** → 退款无法收回内容，这是本模式的固有成本。因此退款政策应偏向"内容与描述不符"而非"我不喜欢"（见第 6 章）。
- **作者已结算** → 需要从后续结算中扣回（M3 才能处理）。

**涉及模块**：2.4 交易、2.8 治理
**阶段**：M3

---

### S10 · 公开市场陌生人购买 + 平台抽成结算

**触发者**：陌生消费者
**前置**：作者已完成实名；平台已接入真实支付通道；skill 可见性为 public
**主流程**
1. 通过搜索发现某作者的 public skill。
2. 正常走 S3 的解锁流程，通过真实支付通道付款。
3. 平台按比例抽成，余款进入作者待结算余额。
4. 周期性结算给作者，出具对账明细。

**异常分支**
- **支付通道回调丢失** → 订单需可查询、可重试、可人工补偿；不能只依赖回调。
- **作者未实名** → 不允许提现（合规要求）。
- **退款发生于结算后** → 从作者后续结算中扣回。

**涉及模块**：2.4 交易结算、2.1 身份、2.8 治理
**阶段**：M3

---

### S11 · 通过 unlisted 链接分享给外部同事

**触发者**：消费者
**前置**：消费者可访问该 skill；分享的对象是**外部人**（不在同一组织）
**主流程**
1. 用户把某个 skill 的 unlisted 链接发给外部同事。
2. 同事可访问该 skill 的 L1/L2，并**按自己的身份独立付费**解锁 L3。

**异常分支**
- **分享者以为"分享链接 = 分享内容"** → 界面必须明确区分"分享 skill（对方仍需自己解锁）"与"分享我的解锁"（后者 M1 不支持，因为技术上无法阻止也不符合商业模式）。这个区分要显式提示，否则会产生大量客诉。
- **同事属于另一个组织** → 组织权益各自独立，不互通。

**涉及模块**：2.2 托管（可见性）、2.3 权益
**阶段**：M1

---

### S12 · 运行时离线降级

**触发者**：网络不可用的 agent 运行环境
**前置**：此前联网时曾落过权益缓存；本次会话处于离线状态
**主流程**
1. 运行时启动，尝试向平台校验权益。
2. 不可达 → 使用本地缓存的权益快照。
3. 缓存覆盖的节点正常可用；缓存未覆盖的付费节点返回 `paywall`（不给内容）。
4. 恢复联网后补做校验与上报。

**异常分支**
- **缓存过期** → 与第 6 章待决问题相关：冷启动且离线时，付费节点应一律不可用（宁可少给，不能多给）。
- **本地缓存被篡改** → 这正是"本地缓存实现 Gate"的已知弱点（M1 接受，M2 换远程）。**离线可用性与付费强度天然矛盾**，这个权衡必须写进产品文档而不是留给工程现场决定。

**涉及模块**：2.5 门控
**阶段**：M1 基本降级 / M2 完整离线策略

---

### S13 · 付费脚本被举报为恶意

**触发者**：消费者 / 平台巡检
**前置**：涉事节点为脚本类；已购用户清单与内容哈希可追溯
**主流程**
1. 举报提交。
2. 平台下架该节点（已购用户立即不可用或回到上一版）。
3. 调查：查看扫描结果、执行记录、作者历史。
4. 处置：警告 / 下架 skill / 封禁作者 / 退还受影响用户。

**异常分支**
- **已购用户正在依赖该节点** → 下架是破坏性的，需要给出过渡（回退到上一可用版本）。这是"下架"与"用户体验"的直接冲突，处置时必须显式权衡。
- **误报** → 作者申诉通道；恢复后应保留其收入记录。
- **作者是内部成员（M1 私有阶段）** → 走组织内部治理流程，不走平台处罚。

**涉及模块**：2.8 治理、2.2 托管、2.4 交易
**阶段**：M2 举报下架 / M3 完整处置与赔付

## 第 4 章 · 关键页面结构

只给结构与字段，不画视觉稿。

### 消费者侧

**Skill 详情页**（本产品的核心页面）
```
┌ skill 头部 ─────────────────────────────┐
│ name · title · 作者 · 可见性徽标          │
│ description（即 L1 全文）                 │
│ 统计：解锁人数 · 更新时间 · 节点数         │
└─────────────────────────────────────────┘
┌ 节点树（页面主体）─────────────────────┐
│ ▸ L1 发现层           免费   [已解锁]    │
│ ▾ L2 正文             免费   [已解锁]    │
│    └ 正文段落列表（可展开阅读）           │
│ ▸ L2#1 进阶：批量处理   ¥5    [解锁]     │
│      teaser：用脚本一次处理 100 条       │
│ ▸ L3 scripts/run.py    ¥8    [解锁]     │
│      teaser：省掉 20 分钟手工步骤        │
│ 合计：解锁全部 ¥13                       │
└─────────────────────────────────────────┘
┌ 我已有的权益 ───────────────────────────┐
│ 个人已解锁：2 个节点                      │
│ 组织已覆盖：1 个节点（来自 XX 组织）       │
└─────────────────────────────────────────┘
```
关键：节点树必须同时展示**免费与付费**，并标出路径位置——用户要能看出"我在哪一步卡住了"。

**我的钱包**：余额 · 充值入口 · 流水（时间、事项、金额、关联 skill/节点）
**我的解锁**：已解锁节点清单 · 来源（自购 / 组织 / 授权）· 解锁时间

### 作者侧

**上传页**：源选择（目录/压缩包/git）→ 解析预览 → 节点派生结果 → 定价表 → 可见性 → 发布
**定价表编辑器**（本产品的作者核心页面）
```
节点            类型   teaser（必填）        价格      数据
L1              免费   —                     —         曝光 1.2k
L2              免费   —                     —         阅读 340
L2#1            细切   [用脚本一次处理100条]  ¥5        撞墙 88 / 解锁 12  ⚠️
L3 scripts/run.py 脚本 [省掉20分钟手工]       ¥8        撞墙 210 / 解锁 176 ✅
```
- teaser 为空时，价格输入框禁用并提示"请先填写 teaser"。
- 每行右侧直接显示诊断（按模块 2.7 的规则），把"定价"从拍脑袋变成看数据。

**数据看板**：转化漏斗（L1 曝光 → L2 阅读 → 撞墙 → 解锁 → 复用）· 各节点诊断 · 收入

### 管理员侧

**成员与组织**：成员列表 · 角色 · 所属组织 · 组织预算余额
**钱包与流水**：充值 · 全量流水检索（按主体 / 时间 / 事项）
**审核队列**（M3）：待审 skill · 更新重审 · 举报工单

### 跨端：解锁请求卡片

同一个 `GateDecision` 有两种呈现形态，**内容一致**：

- **Agent 内**（`ask` 策略触发）：teaser + 价格 + 该节点在路径中的位置 + [解锁] [跳过] + "本次会话后续不再询问同类节点"勾选。
- **Console 内**：同信息 + 余额 + 充值入口。

必须一致，否则用户会觉得"同一个东西两处说法不同"。

## 第 5 章 · 概念模型

概念层实体与关系，不含任何表结构。

```
User ──1:N── Identity(provider, external_id)
  │                provider ∈ {lark, github, email, ...}
  │                飞书只是其中一个 provider
  │
  ├──N:M── Org ──── Wallet
  │         │
  │         └──N:M── Entitlement
  │
  ├──1:N── Skill(owner) ──1:N── Node
  │                              │  kind ∈ {l1, l2, l2#n, l3:path}
  │                              │  title, teaser, relpath
  │                              │
  │                              ├──1:1── Price
  │                              │         source_cents    源价（随源码）
  │                              │         override_cents  覆盖价（console，优先）
  │                              │         effective = override ?? source
  │                              │
  │                              └──N:M── Entitlement
  │
  ├──1:1── Wallet ──1:N── WalletEntry(delta, reason, ref_order)
  │
  └──1:N── Order(subject, node, amount, status, idempotency_key)
                    │
                    └──1:N── Split(payee, amount)   M3 分成
```

**Subject（权益主体）** 是一个抽象：`User` 与 `Org` 都能持有 `Wallet`、`Order`、`Entitlement`。所有涉及"谁付钱、谁拥有"的地方都必须按 Subject 处理，不能写死为用户。

**Entitlement 的键**是 `(subject, skill, node)`。三个设计约束：

1. **不对 Node 做强外键**——节点消失后权益要能存活为孤儿（模块 2.3 设计点三）。
2. **不记录版本**——买断即获得后续更新，所以权益与版本无关。
3. **保留 price_paid 与 acquired_at**——退款、对账、"组织买断后成员自费过"这类场景都要回溯。

**Node 是派生对象，不是作者手写对象。** 作者写的是 SKILL.md 与文件，Node 是系统解析的结果。这个方向不能反——否则作者要维护两套真相。

## 第 6 章 · 待决问题

每个问题给出候选与倾向，不留空白。

### Q1 · 细切标记的具体语法

- **倾向**：`<!-- skill-platform:paywall price=500 title="批量处理" teaser="一次处理100条" -->`
- 理由：HTML 注释在 Markdown 里天然不可见（不影响阅读源码），`key=value` 可复用现有的标量解析逻辑，且不需要改动 frontmatter 解析器（那个解析器很原始，不支持嵌套）。
- 待定：价格单位写分还是元；多条属性缺失时的兜底（倾向：teaser 缺失则拒绝发布该节点）。

### Q2 · 默认价建议算法的依据

- 候选：(a) 纯启发式（按节点类型与文件大小分档）；(b) 同类 skill 的中位数；(c) 不给建议，只给"免费/付费"开关。
- **倾向 (a) + 后续演进到 (b)**。冷启动期没有同类数据，只能启发式；有了数据后按品类中位数更有说服力。
- 无论哪种，**都必须可解释**——作者要能看懂"为什么建议 5 元"，否则不会信任。

### Q3 · 组织预算归属与审批

- 候选：(a) 单一组织钱包，管理员直扣；(b) 部门子钱包 + 审批流；(c) 成员自带额度。
- **倾向 (b)**，但 M1 只做 (a)。内部场景里"谁花的钱"必须能归因到部门，否则财务无法入账。
- 待定：单笔超额走审批还是月度总额管控（倾向：单笔阈值 + 月度总额双控）。

### Q4 · 退款政策

- 候选：(a) 一律不退；(b) 内容与 teaser 严重不符可退；(c) 无条件 N 天内可退。
- **倾向 (b)**。(c) 在本模式下会被滥用（内容已被读取），(a) 又过于强硬。
- 前提：**退款必须由平台介入判定**，不能让系统自动判定"是否相符"——那需要内容语义判断，属于模型不该做的非语言工作。

### Q5 · M1 私有阶段的内容审核强度

- 候选：(a) 完全不审；(b) 只审脚本类节点；(c) 全审。
- **倾向 (a)**。M1 是内部场景，成员之间本就不设防；提前引入审核会严重拖慢上传体验，且没有真实风险对应。
- 但**必须现在就在模型里留出审核状态字段**，否则 M2 加审核时又要动一次全链路。

### Q6 · 离线降级的边界

- 候选：(a) 离线时付费节点一律不可用；(b) 允许本地缓存的权益在 TTL 内离线可用；(c) 允许离线并在联网后补扣。
- **倾向 (b)**，但 TTL 要短（小时级），且**冷启动且从无缓存时一律按不可用处理**（宁可少给，不能多给）。
- (c) 会让"离线"成为绕过付费的手段，不考虑。
- 注意这是第 0 章"防不住复制"之外的另一个诚实边界：**离线可用性与付费强度不可兼得**，产品必须自己选。

### Q7 · 组织买断是否包含未来新增节点

- 候选：(a) 只覆盖购买当时的节点；(b) 覆盖该 skill 的所有未来节点。
- **倾向 (a)**，但要在购买页明确写出——否则组织会以为"买断了这个 skill"，遇到新节点又要付费时产生强烈反弹。
- 折中：提供"订阅该 skill 全部节点"的选项（M3）。

## 第 7 章 · 阶段路线

| 模块 | M1 私有可用闭环 | M2 Web console 与体验 | M3 支付通道与公开市场 |
|---|---|---|---|
| 1 身份与组织 | 建表 + 基础方法（管理员建号） | 注册登录 + 飞书 SSO 跳转 | 实名认证 |
| 2 Skill 托管 | 导入 + 可见性 + 版本快照 | 上传界面 + 在线元数据编辑 | 官方审核队列 |
| 3 节点定价权益 | **全部核心** | 可视化定价表 + 默认价建议 | 促销与动态定价 |
| 4 交易钱包结算 | **钱包 + 充值记账 + 解锁 + 订单幂等** | 组织预算 + 审批流 | 真实支付通道 + 抽成结算 + 退款 |
| 5 分发运行时门控 | **本地 Gate + 未解锁不下发 + 三策略** | 远程 Gate + 离线策略 | 服务端按节点下发 |
| 6 发现与浏览 | CLI 列出 | console 浏览 + 搜索（仅索引 L1） | 推荐与榜单 |
| 7 数据洞察 | 记录事件 | 作者看板 + 节点诊断 | 平台看板 + 漏斗优化建议 |
| 8 信任安全治理 | **无**（内部信任） | 脚本扫描 + 举报下架 | 沙箱 + 审核 + 处置赔付 |

**M1 的验收标准**：一个内部团队能真实跑通「上传 skill → 逐节点定价 → 消费者渐进解锁 → 钱包扣款 → 未解锁内容不下发」的完整闭环。M1 不接真实支付，由管理员记账充值。

**M1 明确不做**：内容审核、沙箱、远程 Gate、真实支付、注册登录界面、推荐算法。

| 维度 | 决定 |

| 版本策略 | 买断即获得后续更新 |
