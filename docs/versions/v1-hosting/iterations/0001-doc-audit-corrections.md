## 为什么

`docs/` 从未被审计过，而它已经积累了两种相反的描述（"skill 落盘" vs "本地不留副本"）、被 ADR 否决的机制、以及**抄写时丢掉限定条件的数字**。

触发点是两轮独立审计（各三路 agent：跨文档一致性、约定与结构、外部事实核查）。其中几项值得记住，因为它们不是笔误：

- **数字复述时丢掉限定条件**：「本机 30 个样本实测 79 tokens」被抄进两条 ADR 后变成「实测 79 tokens」，读起来像普遍事实。
- **引用被编出来**：`kicad-mcp-pro` 兼容矩阵找不到任何出处。
- **修正时要先定口径**：L3 每 skill 合计的中位数，原稿的 29,736 是**"9 个无 L3 的按 0 计入"**算出来的；订正时误按"剔除零值"重算成 148,017，反而改错了。现在两种口径都列在表里。

## 影响

- **不影响任何已交付行为**——实现尚未开始，改的都是设计文档。
- **需要同步改的文档**：已完成（`technical-design.md`、`known-issues.md`、`README.md`、3 条 ADR、`competitors.md`、`blueprint.md`、`docs/README.md`）。`target/blueprint.md` 与 `target/design.md` 只改了事实与失效引用，**产品论证未动**（唯一改变结论方向的是 Agensi 价位那处，已在原地标注）。
- **`known-issues.md` 的 L4 状态变更**：该条是"文档与代码不符"，本轮修掉了根 `README.md` 与 `pyproject.toml`，因此从无标注改为 **`已修复`**；状态图例新增该取值。

- **是否需要新开 ADR**：**不需要**。这些都是事实订正与形式统一，没有引入新的取舍。唯一接近的是 ADR 房规"允许改文件头"的澄清——那是记录方式的澄清，不是架构取舍。
